# 승진 대상자 선정 성능 실험

실험일 2026-11-20 (한국 시간)

## 1. 목적과 사전 가설

회차 2에서 직원 수가 12명, 500명, 2,000명으로 늘어날 때 `runSelection()`이 얼마나 느려지는지 측정했다. 직원마다 전체 이력 배열을 검색하는 ERP 조립 비용은 데이터보다 빠르게 증가하고, 재선정에서는 기존 후보 검색까지 늘어날 것으로 예상했다. 전체 실행에서는 후보별 SQL 쓰기가 가장 큰 비중을 차지할 것으로 예상했다. 멘토링 안내의 선택 과제에서 예측·측정·원인 분석·재측정 순서를 따랐다.

## 3. 데이터 생성

500명 원본을 바이트 단위로 백업했다. 12명은 이 사본의 ERP 5개 테이블에서 가상 직원과 그 이력을 제거해 만들었다. 2,000명 데이터에는 500명 데이터 전체를 포함했다. 가상 직원 488명을 사번순으로 순환하며 각 직원의 소속·직급·날짜와 발령·평가·교육·포상 관계를 복제했다. 신규 사번은 `PERF00489`부터 `PERF01988`까지다. 발령과 포상 ID에는 새 사번을 붙였다. 평가·교육의 복합키와 직원 이름·이메일에도 새 사번을 적용했다. 각 이력에 연결된 직원이 존재하는지 확인했다.

## 4. 실험 방법과 재현

각 규모에서 회차 2 후보가 없는 최초 선정 스냅샷과 기준 코드로 한 번 선정한 재선정 스냅샷을 만들었다. 매 표본 전에 동일한 스냅샷을 `performance.db`에 복원했다. 표본마다 새 Node 프로세스에서 실행했고 버전 실행 순서는 번갈아 바꿨다. DB 복사, 모듈 로드, HR 조회와 결과 검증은 타이머 밖에서 실행했다. 전체 실행 시간은 트랜잭션 완료까지 포함했다.

규모·상태·버전별로 계측 코드가 없는 전체 시간 7회와 구간 시간 7회를 별도로 수집했다. 사전 확인 실행은 통계에서 제외했다. 모든 표본에서 요약 수치, 후보 필드 및 `SELECTION_RUN.detailJson`을 비교했다. 후보의 실행 시각인 `judgedAt`은 비교에서 제외했다.

아래 명령은 `web`에서 실행한다. Windows PowerShell에서 빈 환경변수 할당이 변수를 제거할 수 있으므로 Node에서 토큰을 빈 문자열로 설정한다. 스크립트는 DB 연결 전에 두 환경변수를 검증한다. 실험 중에는 다른 프로세스에서 `performance.db`를 닫아 둔다.

```powershell
$env:DATABASE_URL = 'file:performance.db'
node -e "process.env.DATABASE_AUTH_TOKEN='';import('./scripts/selection-benchmark.mjs')" -- selection 7
node -e "process.env.DATABASE_AUTH_TOKEN='';import('./scripts/selection-tests.mjs')"
node node_modules/typescript/bin/tsc --noEmit --incremental false
```

이번 실행의 `results.json`, `original.db`와 6개 스냅샷은 `web/backups/selection-edg295/`에 있다. 이전 측정값은 `previous-measurements.json`, 기존 12명 DB 사본은 `legacy-12.db`에 보존했다. 백업 디렉터리는 Git에서 무시된다. 스크립트는 종료 시 원본을 복원한다. 강제 종료 후에는 관련 프로세스가 모두 종료됐는지 확인하고 해당 실행 폴더의 `original.db`로 복구한 뒤 빈 `performance.db.selection-lock` 디렉터리를 제거한다.

## 6. 병목 분석

구간 계측 7회의 중앙값이다. 각 칸은 개선 전에서 후로의 변화를 밀리초로 표시한다.

| 직원 수 | 상태 | ERP 조회 | ERP 조립 | 기존 후보 검색 | 후보 upsert | 이력 전체 | JSON 직렬화 |
| ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 12 | 최초 | 3.92 → 3.96 | 0.59 → 0.62 | 0.01 → 0.03 | 17.66 → 12.39 | 0.55 → 0.67 | 0.04 → 0.04 |
| 12 | 재선정 | 4.44 → 3.80 | 0.53 → 0.57 | 0.04 → 0.06 | 17.94 → 11.99 | 0.63 → 0.76 | 0.04 → 0.05 |
| 500 | 최초 | 69.95 → 63.37 | 25.94 → 3.67 | 0.28 → 0.20 | 200.08 → 51.80 | 1.27 → 1.59 | 0.57 → 0.65 |
| 500 | 재선정 | 46.92 → 72.94 | 25.88 → 2.48 | 1.92 → 0.36 | 194.33 → 58.44 | 1.55 → 1.28 | 0.82 → 0.54 |
| 2,000 | 최초 | 186.62 → 162.11 | 497.04 → 7.73 | 0.82 → 0.49 | 666.52 → 116.12 | 5.03 → 3.76 | 2.93 → 2.12 |
| 2,000 | 재선정 | 186.67 → 183.97 | 439.77 → 7.88 | 21.22 → 1.27 | 709.13 → 118.45 | 4.36 → 4.55 | 2.31 → 2.87 |

- **후보별 upsert.** 2,000명 재선정에서 709.13ms로 가장 오래 걸린 계측 구간이었다. 쓰기 문장이 1,836개에서 46개로 줄고 시간이 118.45ms로 감소했다. 12명은 11개에서 1개, 500명은 459개에서 12개로 줄었다. 측정 시간에는 ORM의 SQL 생성과 실행 대기가 포함된다.
- **ERP 조립.** ERP 전체 시간에서 5개 조회 시간을 뺀 값이다. 2,000명 최초 선정에서 497.04ms에서 7.73ms로 줄었다. 기존에는 직원 한 명마다 전체 이력 배열을 훑었다. 개선 후에는 사번별로 모은 행을 조회한다. 조립 시간에는 행 변환과 유효성 검사도 포함된다.
- **기존 후보 검색.** 2,000명 재선정에서 21.22ms에서 1.27ms로 줄었다. 개선 후 수치에는 Map 생성 시간이 포함된다. 최초 선정에서는 기존 후보가 비어 있어 검색 비중이 작았다.
- **선정 이력.** 2,000명에서 선정 근거 JSON은 498,722바이트였다. 개선 전 재선정에서 직렬화 2.31ms를 포함해 총 4.36ms가 걸렸다. 이력은 한 행에 저장하고 타이머는 최종 커밋 전에 끝난다. 이번 규모에서 이력 저장 비중은 작았다.
- **남은 비용.** 2,000명 재선정 개선 후 ERP 조회가 183.97ms로 계측 구간 중 가장 길었다. 조회 코드는 전후 동일했고, 측정값에는 표본 간 편차가 있다.

## 7. 코드 변경과 기능 검증

- `src/services/erp.ts`의 `groupByEmployee()`와 `loadErpEmployees()`는 발령·평가·교육·포상 배열을 각각 한 번 순회해 사번별로 인덱싱한다. 기존 조회 행 순서와 발령 코드 검사를 유지한다.
- `src/services/rounds.ts`의 `runSelection()`은 기존 후보를 사번으로 인덱싱한다. 후보 저장은 SQLite의 999개 바인딩 변수 제한에 맞춰 한 문장당 최대 40행씩 처리한다. 충돌 시 `excluded`에서 현재 행의 값을 읽는다. 수동 조치 적용·자동 취소, 후보 저장과 선정 이력은 같은 트랜잭션에서 처리한다.

| 직원 수 | 전체 후보 | 자동 선정 | 최종 선정 |
| ---: | ---: | ---: | ---: |
| 12 | 11 | 4 | 4 |
| 500 | 459 | 167 | 167 |
| 2,000 | 1,836 | 668 | 668 |

최초 선정과 재선정 모두 같은 요약을 반환했고, 각 조건에서 전후 후보 행과 저장된 판정 근거가 일치했다. 기존 Vitest 테스트 **38개 파일, 309건**이 통과했다. 첫 실행에서는 기존 실험 DB에 `app_session`이 없어 통합 테스트의 시드 단계가 실패했다. 최신 스키마로 빈 `performance.db`를 준비해 재실행하고 종료 후 원본을 복원했다. 별도 Vitest 설정은 기존 테스트의 DB 경로만 바꾼다. TypeScript 검사도 통과했다.

Next.js 로컬 프로덕션 빌드도 통과했다. 첫 빌드에서는 Google Fonts 연결이 막혔다. 네트워크 연결을 허용한 뒤, Next.js CLI를 별도 Node 프로세스에서 실행해 빌드 워커에 부모의 `-e` 옵션이 전달되는 문제를 해결했다. 위와 같은 `DATABASE_URL` 설정에서 사용한 명령은 다음과 같다.

```powershell
node -e "process.env.DATABASE_AUTH_TOKEN='';if(process.env.DATABASE_URL!=='file:performance.db'||process.env.DATABASE_AUTH_TOKEN!=='')throw Error('Unsafe DB target');const r=require('node:child_process').spawnSync(process.execPath,['node_modules/next/dist/bin/next','build'],{stdio:'inherit'});if(r.error)throw r.error;process.exitCode=r.status??1"
```

실험과 테스트를 마친 뒤 `performance.db`의 SHA-256이 원본 백업과 같았고, `local.db`, `test.db`, `.env` 및 기존 12명 DB의 SHA-256도 작업 전과 일치했다.

## 8. 한계와 추가 개선 방향

- 서비스 호출을 순차 측정했다. HTTP, 동시 요청, 브라우저 렌더링과 원격 DB 왕복 시간은 측정 범위 밖이다.
- OS 페이지 캐시와 스케줄러 부하를 통제하지 않았다. 표본마다 프로세스와 DB 상태를 초기화해도 OS 캐시는 남을 수 있다.
- 2,000명 데이터는 기존 가상 직원의 이력 패턴을 재사용한다. 대량 수동 조치와 장기 이력 누적은 별도 데이터 분포로 시험할 수 있다.
- 조립과 쓰기 구간의 차이는 측정값이다. 각 코드 변경의 단독 효과와 메모리 사용량은 측정 범위 밖이다.
- 추가 실험은 ERP 조회 열 축소, 배치 크기 비교, 로컬 동시 요청에서 잠금 대기와 처리량 측정을 후보로 삼을 수 있다.
