> 4. **우선순위로 범위를 조절한다** — P1(필수) → P2(권장) → P3(선택). 시간이 부족하면 P3부터 뺀다.

## 1. 개요

### 1.1 목적

직원 **승진**(직급이 한 단계 오르는 것)과 **승급**(같은 직급 안에서 호봉이 오르는 것) 업무를 시스템으로 처리한다. 지금은 인사팀이 엑셀과 수기로 처리하던 일을, ERP 인사정보를 바탕으로 자동 계산하고, 모든 처리 과정을 기록으로 남기는 것이 목표다.

**승진 업무의 흐름**

1. 인사팀이 승진 회차(예: 2027년 상반기 정기승진)를 만들고 **기준일**을 정한다.
2. 시스템이 기준일 기준으로 ERP 인사정보를 보고 **승진 대상자를 자동 선정**한다. 인사팀은 예외 대상을 직접 추가하거나 제외할 수 있다.
3. 대상자마다 ERP 데이터가 미리 채워진 **신청서**가 만들어진다. 직원은 내용을 확인하고, 틀린 데이터는 **정정 요청**하고, 업무실적을 입력해 **제출**한다.
4. 인사팀은 정정 요청을 승인·반려하고, 신청서를 **검토**해 보완을 요청하거나 **확정**한다.
5. 확정된 신청서로 **심사 자료**를 출력한다.
6. 심사 결과를 등록하고 직원에게 **결과를 안내**한다.

**승급 업무의 흐름**

1. 시스템이 ERP 발령 이력(휴직·징계 등)을 보고 직원마다 **차기승급일**(다음 호봉이 오르는 날)을 자동 계산한다.
2. 인사팀이 수기로 관리하던 대장의 날짜와 **비교**해서 다른 것을 찾는다.
3. 인사팀이 차기승급일을 **확정**한다. 확정 후 발령이 바뀌어 계산 결과가 달라지면 인사팀에 알린다.
4. 직원은 자기 차기승급일을 화면에서 확인하고, 승급이 가까워지거나 승급되면 **안내 메일**을 받는다.

### 1.2 ERP와 Mock ERP

**ERP**(Enterprise Resource Planning)는 대학의 인사·회계·학사 등 업무 데이터를 모아 관리하는 통합 시스템이다. 직원의 직급, 호봉, 발령 이력, 근무평정 같은 인사정보는 ERP에 있다. 본 시스템은 ERP 인사정보를 **읽어서 쓰기만** 하고, ERP를 고치지 않는다.

**Mock**은 테스트나 실습을 위해 실제 대상을 흉내 내어 만든 가짜를 말한다. 실제 UNIST ERP에는 접근할 수 없으므로, 본 시스템과 같은 DB 안에 ERP 역할을 하는 테이블을 만든다. 이 테이블들은 이름이 `src_`(source, 원천)로 시작해서 본 시스템 테이블과 구분된다. 이 문서에서 "ERP", "ERP 데이터"는 모두 이 Mock ERP를 가리킨다.

Mock ERP 데이터는 처음에 시드 데이터(8장)로 채워지고, 이후에는 "Mock ERP 편집" 화면(SCR-13)으로만 바꾼다. ERP 값을 일부러 바꿔 보면서 재계산, 변경 감지, 알림이 제대로 동작하는지 실습하기 위해서다.

| Mock ERP 데이터 | 내용 |
|---|---|
| 부서 | 부서 코드와 이름 |
| 직원 인사마스터 | 사번, 성명, 부서, 직급, 호봉, 입사일, 현 직급 임용일, 현 호봉 승급일, 재직 상태, 퇴직일, 이메일, 휴대전화 |
| 발령 이력 | 임용, 승진, 승급, 휴직(육아·질병·개인사정), 징계(견책·감봉·정직)와 그 기간 |
| 근무평정 | 연도별 평정 등급 (S·A·B·C) |
| 교육이수 | 연도별 교육이수시간 |
| 포상 | 포상 일자와 이름 |
| 수기 승급 대장 | 인사팀이 엑셀로 관리하던 직원별 차기승급일. SFR-006의 비교 대상 |

### 1.3 사용자 역할

| 역할 | 코드 | 할 수 있는 일 | 우선순위 |
|---|---|---|---|
| 인사팀 담당자 | `HR` | 승진 회차·대상자·신청서·결과 관리, 차기승급일 관리, 메일 발송, 이력·접근기록 조회, Mock ERP 편집 | P1 |
| 직원 | `EMPLOYEE` | 본인 신청서 작성·정정 요청·제출, 본인 차기승급일·메일 확인 | P1 |
| 심사위원 | `REVIEWER` | 확정된 신청서 열람과 평가 점수 입력 | P3 |

> 역할에 따라 볼 수 있는 화면과 데이터가 다르므로 **사용자 구분은 P1**이다. 다만 P1에서는 비밀번호 없이 목록에서 사용자를 골라 전환하는 방식(사용자 전환)으로 충분하다. 비밀번호 로그인은 P2다.

## 2. 용어 및 공통 규칙

### 2.1 용어 사전

이 프로젝트에서만 쓰거나, 이 프로젝트에서 특별한 뜻으로 쓰는 용어다. 기술 용어(Next.js, ORM, 트랜잭션 등)는 [README의 기술 용어 사전](../README.md#g-기술-용어-사전)에 있다.

**업무 용어** — 인사 업무에서 쓰는 말

### 2.2 날짜 규칙

- 날짜는 `YYYY-MM-DD` 형식의 문자열이다.
- **기간은 양 끝을 포함한다.** 2024-03-01 ~ 2024-08-31은 184일이다.
- **"n개월 뒤"** 는 같은 날짜로 옮기고, 그 날짜가 없으면 그 달의 마지막 날로 한다. 2026-03-31의 18개월 뒤는 2027-09-30이다.
- **"n일 뒤"** 는 달력으로 n일을 더한다. 2026-07-01의 184일 뒤는 2027-01-01이다.
- **종료일이 없는 휴직**(복직일 미정)은 계산할 때 아직 끝나지 않은 것으로 본다. 승진 계산에서는 기준일까지, 승급 계산에서는 "산정 불가"로 처리한다 (3.4, 3.9).
- **실습 기준일**: 메일 발송처럼 "오늘"이 필요한 기능은 실제 오늘 날짜 대신 화면에서 입력한 기준일을 쓴다. 입력하지 않으면 규칙 설정 `system.default_today`(기본 `2026-11-01`)를 쓴다. 정답표(8장)는 이 날짜를 기준으로 한다. 자동 실행 API(SFR-007)만 실제 오늘 날짜를 쓴다.

### 2.3 공통 표시 규칙

- 직급은 `G6` 대신 `6급`으로 표시한다. 상태 코드(예: `SUBMITTED`)도 화면에는 한글 이름(예: `제출`)으로 표시한다. 한글 이름은 3장의 각 표에 있다.
- **휴대전화는 목록 화면에서 가운데 4자리를 마스킹**한다(`010-2001-1001` → `010-****-1001`). 인사팀이 직원 상세 화면을 열 때만 전체를 보여 주고, 이때 개인정보 접근기록(4.2)을 남긴다.
- 값이 없으면 `-`로 표시한다.
- 확인이 필요한 상태(불일치, 재확인 필요, 정정 요청 대기)는 눈에 띄는 색의 배지로 표시한다.

## 3. 업무 규칙 (가정값)

> 아래 값은 모두 **멘토링용 가정**이며 실제 UNIST 인사규정과 다를 수 있다. 숫자는 코드에 직접 쓰지 말고 설정(규칙 설정 테이블)에서 읽어야 한다 (완료 기준에 포함).

### 3.1 직급과 승진 소요기간 `[가정]`

| 현 직급 | 코드 | 승진 후 직급 | 승진 소요 최저 개월 |
|---|---|---|---|
| 7급 | `G7` | 6급 | 24 |
| 6급 | `G6` | 5급 | 36 |
| 5급 | `G5` | 4급 | 48 |
| 4급 | `G4` | 3급 | 48 |
| 3급 | `G3` | — | 승진 대상 아님 (이 시스템의 최상위 직급) |

### 3.2 기간 산입·불산입 `[가정]`

승진 소요기간과 승급 주기를 셀 때, 아래 기간은 **근무 기간에 넣지 않는다**(불산입).

| 발령 | 유형 | 코드 | 산입 여부 |
|---|---|---|---|
| 휴직 | 육아휴직 | `LEAVE` / `CHILDCARE` | 산입 (근무한 것으로 본다) |
| 휴직 | 질병휴직 | `LEAVE` / `SICK` | **불산입** |
| 휴직 | 개인사정 휴직 | `LEAVE` / `PERSONAL` | **불산입** |
| 징계 | 견책 | `DISCIPLINE` / `REPRIMAND` | 산입 (기간이 없는 처분) |
| 징계 | 감봉 | `DISCIPLINE` / `PAY_CUT` | 산입 (보수만 깎이고 근무는 함) |
| 징계 | 정직 | `DISCIPLINE` / `SUSPENSION` | **불산입** |

**불산입 일수** = 계산 기간과 겹치는 불산입 기간들의 일수 합계. 기간이 계산 기간을 벗어나면 겹치는 부분만 센다.

### 3.3 징계 승진 제한 `[가정]`

징계를 받으면 **징계 종료일부터** 아래 개월 수가 지날 때까지 승진할 수 없다. 견책은 기간이 없으므로 처분일을 종료일로 본다.

| 징계 | 승진 제한 개월 |
|---|---|
| 견책 | 6 |
| 감봉 | 12 |
| 정직 | 18 |

**승진 제한 종료일** = 징계 종료일 + 제한 개월. 징계가 여러 건이면 가장 늦은 종료일을 쓴다.

> 예: 감봉 2026-03-01 ~ 2026-05-31 → 제한 종료일 2027-05-31

### 3.4 승진 대상자 선정 `[가정]`

**판정 대상**: Mock ERP 직원 중 직급이 `G7`~`G4`인 사람 전부 (퇴직자 포함). `G3`은 판정 대상에서 뺀다.

직원마다 승진 회차의 기준일로 아래 3가지를 판정한다. **셋 다 O이면 자동 선정**이다.

| ID | 조건 | O가 되는 경우 |
|---|---|---|
| R1 | 재직·근무 | 재직 상태가 `ACTIVE`이고, 기준일이 어떤 휴직 기간에도 들어 있지 않다 (육아휴직 포함) |
| R2 | 소요기간 | 소요기간 충족일 ≤ 기준일 |
| R3 | 징계 제한 | 징계 이력이 없거나, 기준일 > 승진 제한 종료일 |

**소요기간 충족일 계산**

```
불산입 일수 = 기간 [현 직급 임용일, 기준일]과 겹치는 불산입 기간(3.2)의 일수 합계
            (종료일이 없는 휴직은 기준일까지로 본다)
소요기간 충족일 = (현 직급 임용일 + 승진 소요 최저 개월) + 불산입 일수
```

> 예 (E03): 6급, 현 직급 임용일 2023-07-01, 질병휴직 2024-03-01 ~ 2024-08-31 (184일)
> → 2023-07-01 + 36개월 = 2026-07-01 → + 184일 = **2027-01-01** → 기준일 2026-12-31보다 늦으므로 R2 = X

**예외 처리**

- 인사팀은 자동 판정 결과와 다르게 대상자를 **수동 추가**(자동 미선정 → 대상) 또는 **수동 제외**(자동 선정 → 비대상)할 수 있다. 사유는 필수다(5자 이상).
- 수동 처리는 취소할 수 있다(원래 자동 판정으로 돌아감).
- **최종 대상 여부** = 수동 추가면 대상, 수동 제외면 비대상, 수동 처리가 없으면 자동 판정 결과.
- 선정은 회차가 `PREPARING`일 때 여러 번 다시 실행할 수 있다. 다시 실행하면 자동 판정 값은 새로 계산하고, **수동 처리와 사유는 유지**한다. 이때 수동 추가한 사람이 자동 선정으로 바뀌었거나 수동 제외한 사람이 자동 미선정으로 바뀌면, 수동 처리는 의미가 없어지므로 자동으로 취소한다.
- 선정 결과는 선정 실행 시점의 ERP 값을 복사해 둔다(스냅샷). 이후 ERP가 바뀌어도 선정을 다시 실행하기 전에는 바뀌지 않는다.

### 3.5 승진 회차 상태

| 상태 | 코드 | 이 상태에서 하는 일 |
|---|---|---|
| 준비 | `PREPARING` | 대상자 선정 실행, 예외 처리 |
| 신청 | `APPLYING` | 직원이 신청서 작성·정정 요청·제출. 인사팀이 정정 요청 처리, 신청서 검토 |
| 검토 | `REVIEWING` | 새 제출은 받지 않음 (보완 요청을 받은 사람만 다시 제출). 인사팀이 검토·확정, 심사 자료 출력 |
| 결과 | `RESULT` | 결과 등록, 결과 안내, 심사 자료 출력 |

상태는 위 순서로만 바뀌고, 인사팀이 버튼으로 바꾼다. 되돌릴 수 없다.

| 전환 | 조건 | 전환할 때 일어나는 일 |
|---|---|---|
| 준비 → 신청 | 선정을 1번 이상 실행했고, 최종 대상자가 1명 이상 | 최종 대상자마다 신청서(`NOT_STARTED`)와 주요 데이터 항목(3.7)을 만든다. 대상자에게 신청 안내 메일(`PROMO_INVITE`)을 보낸다 |
| 신청 → 검토 | 없음 | 작성 전·작성 중인 신청서는 그대로 남는다 (= 미제출) |
| 검토 → 결과 | 제출(`SUBMITTED`)·보완 요청(`RETURNED`) 상태 신청서가 없고, 처리 대기 중인 정정 요청이 없다 | 없음 |

### 3.6 신청서 상태와 규칙

| 상태 | 코드 | 뜻 |
|---|---|---|
| 작성 전 | `NOT_STARTED` | 신청서가 만들어졌지만 직원이 아직 저장하지 않음 |
| 작성 중 | `DRAFT` | 직원이 한 번 이상 임시저장함 |
| 제출 | `SUBMITTED` | 직원이 제출함. 인사팀 검토 대기 |
| 보완 요청 | `RETURNED` | 인사팀이 돌려보냄. 직원이 고쳐서 다시 제출해야 함 |
| 확정 | `CONFIRMED` | 인사팀이 확정함. 더 이상 수정할 수 없음 |

**직원이 할 수 있는 일**

| 일 | 가능한 경우 | 결과 |
|---|---|---|
| 임시저장 (업무실적·자기개발 계획) | 회차가 `APPLYING`이고 신청서가 `NOT_STARTED`·`DRAFT` / 또는 신청서가 `RETURNED` (회차 상태 무관) | `NOT_STARTED`이면 `DRAFT`로 바뀜. 나머지는 상태 유지 |
| 정정 요청 | 임시저장이 가능한 경우와 같음 | 정정 요청 `PENDING` 생성 (3.8) |
| 제출 | 임시저장이 가능한 경우와 같고, 아래 제출 조건을 만족 | `SUBMITTED` |

**제출 조건**: 주요 업무실적이 1자 이상 2,000자 이하이고, 자기개발 계획이 1,000자 이하이고, 이 신청서에 처리 대기(`PENDING`) 중인 정정 요청이 없다.

- 제출 버튼은 입력 내용을 저장하면서 제출한다. 작성 전(`NOT_STARTED`) 상태에서 바로 제출해도 "작성 중"을 거친 것으로 보고 처리 이력 `APP_DRAFTED`를 먼저 한 번 남긴다.
- 조건을 만족하지 않으면 이유를 보여 주고, **아무것도 저장하지 않는다** (입력한 내용은 화면에 그대로 남아 있어 임시저장할 수 있다).

**인사팀이 할 수 있는 일** (회차가 `APPLYING` 또는 `REVIEWING`일 때)

| 일 | 대상 | 결과 |
|---|---|---|
| 보완 요청 | `SUBMITTED` 신청서 | `RETURNED`. 사유 필수 |
| 확정 | `SUBMITTED` 신청서 | `CONFIRMED` |

### 3.7 신청서 주요 데이터 항목

신청서를 만들 때 아래 항목을 ERP에서 가져와 채운다. 각 항목은 **ERP 값**(만들 때의 값, 바뀌지 않음)과 **현재 값**(정정 승인 시 바뀜)을 따로 가진다. 처음에는 둘이 같다. 근무평정·교육이수 연도는 **기준일이 속한 연도를 포함한 최근 3년**이다 (기준일 2026-12-31이면 2024·2025·2026).

| 순서 | 항목 키 | 이름 | 값 | 정정 요청 |
|---|---|---|---|---|
| 1 | `name` | 성명 | ERP 성명 | 불가 |
| 2 | `org` | 소속 | 부서 이름 | 가능 |
| 3 | `grade` | 현 직급 | `6급` | 불가 |
| 4 | `target_grade` | 승진 예정 직급 | `5급` | 불가 |
| 5 | `hire_date` | 입사일 | 날짜 | 가능 |
| 6 | `grade_date` | 현 직급 임용일 | 날짜 | 가능 |
| 7 | `qualify_date` | 소요기간 충족일 | 대상자 선정 결과의 값 | 불가 |
| 8~10 | `rating_2024` ~ `rating_2026` | 2024~2026년 근무평정 | `S`·`A`·`B`·`C`, 없으면 `-` | 가능 |
| 11~13 | `training_2024` ~ `training_2026` | 2024~2026년 교육이수시간 | 숫자 (예: `30`), 없으면 `-` | 가능 |
| 14 | `awards` | 포상 | `일자 이름`을 일자순으로 `, `로 연결. 없으면 `없음` | 가능 |
| 15 | `disciplines` | 징계 | `시작일 유형명`을 일자순으로 `, `로 연결. 없으면 `없음` | 가능 |

> 예 (E06 강서연): 포상 `2024-05-15 우수직원 표창`, 징계 `2025-01-15 견책`

**직원 입력 항목**: 주요 업무실적(필수, 2,000자 이하), 자기개발 계획(선택, 1,000자 이하)

### 3.8 정정 요청 규칙

- 직원은 정정 가능한 항목(3.7)마다 **바라는 값**과 **사유**(필수)를 적어 정정을 요청한다.
- 한 항목에 처리 대기(`PENDING`) 중인 요청이 있으면 그 항목에는 새로 요청할 수 없다.
- 인사팀 처리:
  - **승인** (`APPROVED`): 반영할 값을 입력한다(기본값은 직원이 바란 값). 그 항목의 **현재 값**이 반영 값으로 바뀐다. ERP 값과 ERP 자체는 바뀌지 않는다.
  - **반려** (`REJECTED`): 피드백(사유)이 필수다. 현재 값은 그대로다.
- 정정 승인은 **대상자 판정(R1~R3)을 다시 하지 않는다.** 예를 들어 현 직급 임용일을 정정해도 소요기간 충족일은 바뀌지 않는다. 판정에 영향을 주는 정정이라면 인사팀이 ERP를 고친 뒤 예외 처리로 해결한다(실제 업무에서도 판정은 ERP 기준이다).
- 직원은 처리 결과(승인 값 또는 반려 피드백)를 자기 신청서에서 볼 수 있다.

### 3.9 차기승급일 산정 `[가정]`

**관리 대상**: Mock ERP의 모든 직원. 단, 퇴직자(`RETIRED`)는 **관리 제외**(`EXCLUDED`)로 표시만 하고 계산하지 않는다.

```
기본 차기승급일 = 현 호봉 승급일 + 승급 주기(12개월)
불산입 일수     = 기간 [현 호봉 승급일, 차기승급일 전날]과 겹치는 불산입 기간(3.2)의 일수 합계
차기승급일      = 기본 차기승급일 + 불산입 일수
```

불산입 일수를 더해 차기승급일이 늦춰지면 계산 기간도 길어지므로, 늘어난 기간에 다른 불산입 기간이 더 겹칠 수 있다. 그래서 **차기승급일이 더 이상 바뀌지 않을 때까지 위 계산을 반복**한다.

- **산정 불가** (`UNDETERMINED`): 종료일이 없는(복직일 미정) 불산입 휴직이 있으면, 늦춰질 일수를 알 수 없으므로 계산하지 않는다.
- 육아휴직과 감봉은 산입이므로 차기승급일에 영향이 없다.

> 예 (E12): 현 호봉 승급일 2026-07-01, 질병휴직 2026-08-01 ~ 2026-09-30 (61일)
> → 2026-07-01 + 12개월 = 2027-07-01 → + 61일 = **2027-08-31**

### 3.10 수기 대장 비교와 확정

자동 산정값과 수기 대장 값을 비교해 아래 상태로 표시한다.

| 비교 상태 | 코드 | 조건 |
|---|---|---|
| 일치 | `MATCH` | 둘이 같음 |
| 불일치 | `MISMATCH` | 둘이 다름 |
| 수기값 없음 | `NO_MANUAL` | 수기 대장에 그 직원이 없거나 날짜가 비어 있음 |
| 산정 불가 | `UNDETERMINED` | 3.9의 산정 불가 |
| 관리 제외 | `EXCLUDED` | 퇴직자 |

**확정**

- 인사팀이 직원별로 차기승급일을 **확정**한다. 확정값이 직원에게 보이는 차기승급일이다.
  - **자동값으로 확정** (`AUTO`): 자동 산정값을 확정값으로 한다. 산정 불가·관리 제외면 할 수 없다.
  - **직접 입력으로 확정** (`MANUAL`): 날짜를 직접 입력한다. 사유가 필수다. 산정 불가인 직원은 이 방법으로만 확정할 수 있다.
- **일치 건 일괄 확정**: 비교 상태가 `MATCH`이고 아직 확정하지 않은 직원을 한 번에 자동값으로 확정한다.
- **재계산과 변경 감지**: 재계산하면 모든 직원의 자동 산정값과 비교 상태를 새로 구한다. 이미 확정한 직원의 자동 산정값이 **이전 자동 산정값과 달라지면** "재확인 필요"(`review_needed = Y`)로 표시하고 인사팀 알림(`STEP_CHANGED`)을 만든다. 확정값은 그대로 둔다. 인사팀이 다시 확정하면 "재확인 필요"가 풀린다.
- 재계산은 멱등이다. ERP가 바뀌지 않았다면 다시 실행해도 처리 이력과 알림이 늘지 않는다.

### 3.11 메일 종류와 발송 규칙

실제 메일은 보내지 않는다. 보낼 메일을 **메일 발송함**에 쌓고, 화면에서 내용을 확인한다. 메일마다 **중복 발송 방지 키**가 있어서, 같은 키의 메일이 이미 있으면 다시 쌓지 않는다.

| 종류 | 코드 | 받는 사람 | 보내는 때 | 중복 발송 방지 키 | 제목 |
|---|---|---|---|---|---|
| 승진 신청 안내 | `PROMO_INVITE` | 최종 대상자 | 회차가 `APPLYING`으로 바뀔 때 | `PROMO_INVITE|회차ID|사번` | `[승진] {회차명} 신청 안내` |
| 승진 결과 안내 | `PROMO_RESULT` | 결과가 등록된 신청자 | 인사팀이 "결과 안내 발송"을 누를 때 | `PROMO_RESULT|회차ID|사번` | `[승진] {회차명} 결과 안내` |
| 승급 예정 안내 | `STEP_NOTICE` | 확정 차기승급일이 기준일 다음 날부터 30일 이내인 재직자 | "승급 안내 발송" 실행 시 | `STEP_NOTICE|사번|차기승급일` | `[승급] 차기 승급 예정 안내 ({차기승급일})` |
| 승급 결과 안내 | `STEP_RESULT` | 기준일 30일 전부터 기준일까지 사이에 승급(`STEP_UP`) 발령이 난 재직자 | "승급 안내 발송" 실행 시 | `STEP_RESULT|발령ID` | `[승급] 승급 결과 안내 ({호봉}호봉)` |

- "30일"은 규칙 설정 `mail.step_notice_days`, `mail.step_result_days`에서 읽는다.
- 승급 예정 안내는 **확정값**만 기준으로 한다. 확정하지 않은 직원에게는 보내지 않는다.
- 본문에는 받는 사람 성명과 핵심 내용(회차명·결과, 차기승급일, 새 호봉)을 넣는다. 문구는 자유다.

### 6.1 주요 화면의 표시 항목

**SCR-03 대상자 선정**

- 상단: 회차명, 기준일, 상태, "선정 실행" 버튼(`PREPARING`일 때만), 판정 대상·자동 선정·최종 대상 인원
- 표: 사번, 성명, 소속, 현 직급 → 승진 예정 직급, 현 직급 임용일, 소요 개월, 불산입 일수, 소요기간 충족일, R1, R2, R3, 승진 제한 종료일, 자동 선정, 예외 처리(추가·제외·없음)와 사유, **최종 대상**
- 행마다 "수동 추가"(자동 미선정일 때) 또는 "수동 제외"(자동 선정일 때), 예외 처리가 있으면 "취소" 버튼 (`PREPARING`일 때만)

**SCR-05 신청서 검토**

- 상단: 회차명, 신청자(사번·성명·소속), 신청서 상태, 보완 요청·확정 버튼
- 주요 데이터 표: 항목 이름, ERP 값, 현재 값 (다르면 강조), 정정 요청 상태
- 정정 요청 표: 항목, 바라는 값, 사유, 상태, 처리(승인 시 반영 값 입력 / 반려 시 피드백 입력)
- 직원 입력: 주요 업무실적, 자기개발 계획
- 처리 이력: 이 신청서와 그 정정 요청의 이력 (시각순)

**SCR-08 차기승급일 관리**

- 상단: "재계산" 버튼, "일치 건 일괄 확정" 버튼, 비교 상태별 인원, 재확인 필요 인원
- 표: 사번, 성명, 직급, 호봉, 현 호봉 승급일, 불산입 일수, 자동 산정값, 수기 대장 값, 비교 상태, 확정값, 확정 방식, 재확인 필요
- 행을 누르면 상세: 계산 근거(불산입 기간 목록과 각 일수, 반복 계산 과정), 휴대전화(전체 표시, 접근기록), 확정 폼, 처리 이력

**SCR-22 내 승진 신청서**

- 상단: 회차명, 상태, 인사팀 보완 요청 사유(있으면), 결과(안내 후)
- 주요 데이터 표: 항목, 현재 값, 정정 요청 버튼(가능할 때), 진행 중인 정정 요청 상태
- 직원 입력 폼: 주요 업무실적(글자 수 표시), 자기개발 계획, 임시저장·제출 버튼
- 정정 요청 내역: 항목, 바라는 값, 사유, 상태, 처리 결과

### 7.3 보안 (원본 SER·COR 중 구현 가능한 것)

- 실제 개인정보는 쓰지 않는다. 시드 데이터는 모두 가상이며, 메일 주소는 `@unist.example`이다.
- 역할별 접근 제어(008-02)는 화면 메뉴를 숨기는 것만으로는 부족하다. **서버에서** 현재 사용자의 역할과 본인 여부를 확인해야 한다.
- 개인정보 마스킹(2.3)과 접근기록(4.2).
- SQL은 문자열을 이어 붙여 만들지 않는다(값은 파라미터로). 사용자 입력은 서버에서 길이·형식을 검증한다. 오류 화면에 SQL이나 스택 같은 내부 정보를 보여 주지 않는다 (원본 SER-007).
- 비밀번호는 해시로 저장한다 (P2, 008-06). DB 접속 정보 등 비밀값은 환경변수로 관리하고 커밋하지 않는다.
- 인사팀 화면은 허용한 IP에서만 열린다 (원본 SER-002 "관리자 기능은 내부망에서만", P3).
