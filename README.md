# 직원 승진승급 관리시스템 — 멘토링 프로젝트 가이드

UNIST 「직원 승진승급 프로세스 구축」 제안요청서(RFP)를 바탕으로, 실제 인사 업무 시스템과 비슷한 웹 서비스를 **혼자서 처음부터** 만들고, 마지막에 GitHub에 올려 호스팅까지 시도해 보는 프로젝트입니다.

이 README는 **어떻게 만드는지**를 순서대로 안내합니다. **무엇을 만드는지**는 [docs/요구사항.md](docs/요구사항.md)에 있습니다.

### 진행 방식

- 이 폴더(zip)를 받은 뒤 **혼자서** Step 1부터 진행합니다. 중간 점검은 없습니다.
- 버전 관리는 **내 컴퓨터의 Git**으로 합니다 (Step 3에서 시작). Step마다 커밋합니다.
- 마지막 Step에서 GitHub에 올리고 호스팅을 시도한 뒤, 회고를 써서 멘토에게 보내면 멘토링이 끝납니다.

## 프로젝트 소개

### 무엇을 만드나

대학 인사팀이 직원 **승진**(직급이 오르는 것)과 **승급**(호봉이 오르는 것)을 처리하는 **업무 시스템**입니다. 실제 사업은 UNIST의 ERP(SAP) 안에 기능을 추가하는 것이지만, 이 프로젝트에서는 ERP를 흉내 낸 가짜 데이터 위에 독립적인 웹 서비스로 만듭니다.

- **인사팀**은 승진 대상자를 자동으로 뽑고, 직원이 낸 신청서를 검토·확정하고, 심사 자료를 출력하고, 결과를 안내합니다. 직원마다 다음 호봉이 오르는 날(차기승급일)을 자동 계산해 수기 대장과 비교하고 확정합니다.
- **직원**은 ERP 데이터가 미리 채워진 승진 신청서를 확인하고, 틀린 데이터는 정정을 요청하고, 업무실적을 입력해 제출합니다. 자기 차기승급일과 안내 메일을 확인합니다.

### 이 프로젝트에서 배우는 것

- 모호한 RFP를 명확한 명세로 바꾼 문서를 읽고, 명세대로 끝까지 구현하는 경험
- 업무 시스템의 핵심 패턴: **상태 전이(워크플로), 규칙 기반 자동 계산, 처리 이력, 역할별 권한, 개인정보 접근기록**
- 날짜 계산처럼 틀리기 쉬운 로직을 테스트로 검증하는 습관
- Git 버전 관리, GitHub 업로드, 호스팅 환경이 로컬과 어떻게 다른지
- AI 코딩 도구를 쓰되, 결과를 명세와 테스트로 검증하는 방법

## 핵심 개념 — 시작 전에 꼭 알아야 할 것

이 프로젝트에는 인사 업무 용어와 프로젝트 고유 용어가 많습니다. Step 1을 시작하기 전에 이 절을 한 번 읽어 두면 나머지 문서를 훨씬 쉽게 읽을 수 있습니다. 전체 용어 목록은 [요구사항 2.1 용어 사전](docs/요구사항.md#21-용어-사전)과 [G. 기술 용어 사전](#g-기술-용어-사전)에 있습니다.

### 1. 승진과 승급은 다르다

|                     | 승진                                                | 승급                                                  |
| ------------------- | --------------------------------------------------- | ----------------------------------------------------- |
| 무엇이 오르나       | **직급** (7급 → 6급)                                | **호봉** (4호봉 → 5호봉), 직급은 그대로               |
| 언제                | 승진 회차마다 심사를 거쳐                           | 정해진 주기(12개월)마다 자동으로                      |
| 이 시스템이 하는 일 | 대상자 선정 → 신청서 → 검토 → 심사 자료 → 결과 안내 | 차기승급일 계산 → 수기 대장과 비교 → 확정 → 안내 메일 |
| 요구사항            | SFR-001 ~ 004                                       | SFR-005 ~ 007                                         |

### 2. 인사 데이터는 "ERP"에서 읽는다 — 이 프로젝트에서는 가짜 ERP

직원의 직급·호봉·발령 이력·근무평정 같은 인사정보는 원래 **ERP**(대학의 통합 업무 시스템)에 있습니다. 본 시스템은 ERP를 고치지 않고 **읽기만** 합니다.

우리는 실제 UNIST ERP에 접근할 수 없으므로, **ERP를 흉내 낸 가짜 테이블을 같은 DB 안에 만들어 씁니다.** 이렇게 실제를 흉내 낸 가짜를 **Mock(목)** 이라고 합니다. Mock ERP 테이블은 이름이 `src_`(source, 원천)로 시작합니다.

| 진짜 ERP라면                       | 이 프로젝트에서는                             |
| ---------------------------------- | --------------------------------------------- |
| 인사마스터 (직원 기본정보)         | `src_employee`                                |
| 발령 이력 (승진, 승급, 휴직, 징계) | `src_appointment`                             |
| 근무평정, 교육이수, 포상           | `src_evaluation`, `src_training`, `src_award` |
| 인사팀 엑셀 대장                   | `src_manual_step_ledger`                      |

### 3. 휴직·징계 기간은 근무 기간에서 빠질 수 있다 — "불산입"

승진하려면 현 직급에서 일정 기간(예: 6급은 36개월) 근무해야 하고, 호봉은 12개월마다 오릅니다. 그런데 **질병휴직, 개인사정 휴직, 정직 기간은 근무 기간에 넣지 않습니다**(불산입). 그만큼 승진 가능 날짜와 차기승급일이 늦춰집니다. 육아휴직은 근무한 것으로 봅니다(산입).

> 예: 6급 박민재(E03)는 2023-07-01에 6급이 되었고 36개월이 지나면 2026-07-01입니다. 그런데 질병휴직 184일이 있어서 **2027-01-01**에야 조건을 채웁니다. 기준일이 2026-12-31이므로 **딱 하루 차이로** 자동 선정에서 빠집니다.

이런 날짜 계산이 이 프로젝트의 핵심이자 가장 틀리기 쉬운 부분입니다. 그래서 날짜 함수(`docs/starter/date.ts`)는 미리 만들어 두었고, 규칙 함수는 Step 5에서 테스트부터 작성합니다.

### 4. 업무는 "상태"를 따라 진행된다

승진 업무는 정해진 순서대로 상태가 바뀝니다. 상태마다 할 수 있는 일이 다릅니다.

```
승진 회차:   준비 ──▶ 신청 ──▶ 검토 ──▶ 결과
            (대상자 선정)  (작성·제출)  (확정·심사자료)  (결과 안내)

신청서:     작성 전 ──▶ 작성 중 ──▶ 제출 ──▶ 확정
                                     │  ▲
                              보완 요청 ▼  │ 다시 제출
                                    보완 요청

정정 요청:  처리 대기 ──▶ 승인 (신청서 값이 바뀜)
                     └─▶ 반려 (피드백만 남음)
```

"지금 상태에서 이 버튼을 눌러도 되는가"를 판단하는 규칙이 요구사항 3.5~3.8에 표로 정리되어 있습니다.

### 5. 모든 처리는 "처리 이력"에, 개인정보 열람은 "접근기록"에 남는다

- **처리 이력**: 신청서 제출, 정정 승인, 보완 요청, 차기승급일 확정처럼 상태가 바뀔 때마다 **누가·언제·무엇을·어떤 상태에서 어떤 상태로·왜** 했는지 남깁니다. RFP의 "투명성 강화" 목표입니다.
- **개인정보 접근기록**: 인사팀이 다른 직원의 개인정보를 **열람·다운로드·인쇄·수정**할 때마다 계정·일시·IP·정보주체·수행업무를 남깁니다. RFP 보안 요구사항(SER)입니다.

### 6. 메일은 진짜로 보내지 않는다 — "메일 발송함"

신청 안내, 결과 안내, 승급 안내 메일은 실제로 보내지 않고 **메일 발송함 테이블에 쌓아서** 화면으로 확인합니다. 같은 메일이 두 번 쌓이지 않도록 메일마다 **중복 발송 방지 키**를 붙입니다. 발송 버튼을 여러 번 눌러도 결과가 같은 성질을 **멱등성**이라고 합니다.

### 7. "오늘"은 2026-11-01로 고정한다 — 실습 기준일

메일 대상("30일 안에 승급하는 사람")처럼 오늘 날짜에 따라 결과가 바뀌는 기능은, 실습 결과가 날짜마다 달라지지 않도록 **화면에서 입력한 기준일**을 오늘로 씁니다. 기본값은 `2026-11-01`이고, 정답표도 이 날짜를 기준으로 합니다.

### 8. 사용자는 셋, P1에서는 "사용자 전환"으로 바꿔 가며 쓴다

| 역할                      | 사용자 ID         | 쓰는 화면     |
| ------------------------- | ----------------- | ------------- |
| 인사팀 (`HR`)             | `hr01`            | `/hr/...`     |
| 직원 (`EMPLOYEE`)         | `u1001` ~ `u1012` | `/me/...`     |
| 심사위원 (`REVIEWER`, P3) | `reviewer01`      | `/review/...` |

## Step 16 — GitHub에 올리고 호스팅해 보기

**목표**: 코드가 GitHub에 올라가 있고, Vercel에 배포를 시도해 **로컬에서 쓰던 SQLite 파일 DB가 호스팅 환경에서 왜 동작하지 않는지** 직접 확인하고 해결 방향을 정리했다.

> 이 Step은 시작 파일 검증 범위 밖입니다. GitHub·Vercel의 메뉴 이름은 바뀔 수 있으니, 다르면 비슷한 이름을 찾거나 공식 문서를 봅니다.

### 16-1. GitHub에 올리기

1. GitHub에 로그인하고 오른쪽 위 `+` → **New repository**를 누릅니다.
   - Repository name: `promotion-mentoring`
   - **Private** 선택 (원본 RFP 요구사항이 들어 있으므로)
   - "Add a README file" 등 초기화 옵션은 **모두 끕니다**
2. 프로젝트 폴더에서 실행합니다.

```bash
git remote add origin https://github.com/<내 계정>/promotion-mentoring.git
git push -u origin main
```

3. GitHub 저장소 페이지에서 `web/`, `docs/`, `README.md`가 보이고, `web/.env`와 `web/local.db`는 **없는지** 확인합니다.

### 16-2. Vercel에 배포하기

1. [vercel.com](https://vercel.com)에 **GitHub 계정으로** 가입합니다 (Hobby 무료 플랜).
2. **Add New → Project**에서 `promotion-mentoring` 저장소를 **Import**합니다.
3. **Root Directory**를 `web`으로 지정합니다. 빠뜨리면 빌드가 실패합니다.
4. **Environment Variables**에 로컬 `.env`와 같은 값을 넣습니다.

| 이름             | 값                                       |
| ---------------- | ---------------------------------------- |
| `DATABASE_URL`   | `file:local.db`                          |
| `CRON_SECRET`    | 임의의 긴 문자열                         |
| `SESSION_SECRET` | Step 13 로그인을 했다면 임의의 긴 문자열 |

5. **Deploy**를 누릅니다. 2~3분 뒤 `https://promotion-mentoring-xxxx.vercel.app` 형태의 주소가 생깁니다.

### 16-3. 결과 확인 — 화면에서 오류가 나는 것이 정상입니다

- 빌드는 **성공**합니다. 모든 페이지가 `force-dynamic`이라 빌드할 때 DB에 접근하지 않기 때문입니다.
- 배포 주소에서 사용자 전환 화면처럼 DB를 쓰는 화면을 열면 **오류(500)** 가 납니다.
- Vercel 프로젝트의 **Logs**(또는 Deployments → 해당 배포 → Runtime Logs)에서 DB 관련 오류 메시지를 찾아 회고에 적습니다.

**왜 안 되나**

| 원인                                 | 설명                                                                                                                                                                                   |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DB 파일이 없다                       | `local.db`는 `.gitignore`에 있어서 GitHub에 올라가지 않았고, Vercel은 GitHub의 코드만 가져간다                                                                                         |
| 파일에 써도 남지 않는다              | Vercel은 **서버리스** 환경이다. 요청을 처리하는 실행 환경이 수시로 새로 만들어지고, 앱 폴더는 읽기 전용이다. DB 파일을 함께 올려도 신청서 제출 같은 쓰기는 저장되지 않거나 곧 사라진다 |
| 실행 환경끼리 파일을 공유하지 않는다 | 요청이 몰리면 실행 환경이 여러 개 뜨고 각자 자기 파일을 본다. 한 곳에서 쓴 데이터가 다른 곳에서 보이지 않는다                                                                          |

즉, **DB를 앱과 같은 서버의 파일로 두는 방식은 서버리스 호스팅과 맞지 않습니다.** DB를 앱 밖의 별도 서비스로 분리해야 합니다.

### 16-4. 해결 방향 (조사만 하고 구현하지 않음)

이 프로젝트는 여기까지 합니다. 아래 방법을 읽어 보고, **어떤 방법을 고를지와 그 이유**를 회고에 적습니다.

### A-6. 코드 규칙

1. **업무 규칙의 숫자를 코드에 직접 쓰지 않는다.** 소요 개월, 제한 개월, 승급 주기, 메일 일수는 `loadRules()`로 `rule_config`에서 읽는다.
2. **`src/domain/`은 DB를 import하지 않는다.** 필요한 값은 인자로 받는다.
3. **날짜 계산은 `src/domain/date.ts`의 함수만 쓴다.** `new Date()`로 날짜를 더하거나 빼지 않는다 (시간대 때문에 하루가 밀린다). 날짜 비교는 문자열 비교(`a <= b`)로 한다.
4. **상태를 바꾸는 모든 처리는 `src/services/`의 함수 하나로 만든다.** 그 함수 안에서 ① 현재 사용자 권한 확인 ② 규칙 검사(위반이면 `BusinessError`) ③ `db.transaction` 안에서 쓰기 + `recordHistory` (+ 알림·메일) 순서로 처리한다.
5. **권한 확인은 서버에서 한다.** `hr/layout.tsx`의 `requireRole`은 화면만 막는다. **Server Action은 레이아웃을 거치지 않고 직접 호출될 수 있으므로**, 서비스 함수(또는 Server Action) 안에서도 역할과 본인 여부를 다시 확인한다.
6. **집계·검증 쿼리는 SQL로 직접 쓴다** (Drizzle의 `sql` 템플릿). 단순 조회·저장은 Drizzle 문법을 쓴다. 문자열을 이어 붙여 SQL을 만들지 않는다.
7. **페이지는 Server Component로 만든다.** 브라우저 상호작용이 꼭 필요한 작은 컴포넌트(예: 글자 수 표시)에만 `'use client'`를 붙인다.
8. **표시 형식(직급 이름, 상태 한글명, 마스킹, `-`)은 `src/lib/format.ts`** 한 곳에서 처리한다.
9. **오류 화면에 내부 정보를 보여 주지 않는다.** `BusinessError`의 메시지만 사용자에게 보여 주고, 그 밖의 오류는 "처리 중 오류가 발생했습니다"로 보여 준다 (원본 SER-007).

### A-7. 화면 코드 패턴

아래 코드는 이 버전(Next.js 16.4.3)에서 빌드와 실행을 확인한 패턴입니다.

**① 쿼리 파라미터를 받는 페이지** — `searchParams`는 **Promise**이므로 `await`합니다. `PageProps<'/경로'>` 타입은 Next.js가 자동으로 만들어 줍니다.

```tsx
// src/app/hr/steps/page.tsx
export default async function StepsPage({
  searchParams,
}: PageProps<"/hr/steps">) {
  const { status } = await searchParams; // string | string[] | undefined
  return <main>…</main>;
}
```

**② 동적 경로** — `params`도 Promise입니다.

```tsx
// src/app/hr/applications/[appId]/page.tsx
export default async function ReviewPage({
  params,
}: PageProps<"/hr/applications/[appId]">) {
  const { appId } = await params; // 문자열이므로 Number(appId)로 변환
  return <main>…</main>;
}
```

**③ 폼 → Server Action → 결과 페이지로 이동, 규칙 위반은 쿼리로 전달**

```ts
// src/app/hr/rounds/[roundId]/candidates/actions.ts
"use server";

import { redirect } from "next/navigation";
import { BusinessError } from "@/lib/errors";
import { getCurrentUser } from "@/lib/session";
import { setManualAction } from "@/services/rounds";

export async function manualAddAction(formData: FormData) {
  const roundId = Number(formData.get("roundId"));
  const empNo = String(formData.get("empNo"));
  const reason = String(formData.get("reason") ?? "");
  const me = await getCurrentUser();
  let error = "";
  try {
    await setManualAction(me, roundId, empNo, "ADD", reason);
  } catch (e) {
    if (e instanceof BusinessError) error = e.message;
    else throw e;
  }
  // redirect는 try 안에서 부르지 않는다 (redirect는 내부적으로 예외를 던져서 catch에 잡힌다)
  redirect(
    `/hr/rounds/${roundId}/candidates${error ? `?error=${encodeURIComponent(error)}` : ""}`,
  );
}
```

## C. 주요 처리 절차

요구사항 3~4장을 코드 순서로 풀어 쓴 것입니다.

### C-1. 선정 실행

```
1. 권한 확인 (HR), 회차가 PREPARING인지 확인
2. rules = loadRules()
3. Mock ERP에서 직급 G7~G4인 직원 전부와 각자의 발령 이력을 읽는다
4. db.transaction:
   직원마다
     j = judgeCandidate(입력, 회차.baseDate, rules)
     기존 행 = promotion_candidate(회차, 사번)
     manualAction = 기존 행?.manualAction ?? 'NONE'
     수동 처리가 의미 없어졌으면 (ADD인데 j.autoSelected, EXCLUDE인데 !j.autoSelected)
        manualAction = 'NONE', 사유 비움, 처리 이력 MANUAL_CANCEL (사유 "재선정으로 자동 취소")
     행 저장 (있으면 수정, 없으면 추가): j의 값 + 스냅샷(성명, 부서명…) + manualAction + finalSelected(...)
   처리 이력 SELECTION_RUN (상세: { total, auto, final })
```

### C-2. 회차 상태 전환

```
PREPARING → APPLYING
  조건: promotion_candidate 행이 있고, final_selected = 'Y'가 1명 이상
  db.transaction:
    회차.status = APPLYING, 이력 ROUND_STATUS_CHANGED
    최종 대상자마다
      application 추가 (NOT_STARTED), 이력 APP_CREATED
      items = buildApplicationItems(ERP 현재 값, 대상자 판정, 기준일) → application_item 15행 (erp_value = current_value)
      queueMail(PROMO_INVITE)

APPLYING → REVIEWING
  조건 없음. 회차.status만 바꾸고 이력

REVIEWING → RESULT
  조건: 이 회차에 status가 SUBMITTED·RETURNED인 신청서가 없고, PENDING 정정 요청이 없다
  회차.status만 바꾸고 이력
```

### C-3. 신청서 제출

```
1. 신청서를 읽고 본인 것인지 확인 (me.empNo = application.emp_no)
2. 편집 가능한지 확인 (요구사항 3.6 표)
3. 제출 조건 확인: 업무실적 1~2000자, 계획 ≤1000자, PENDING 정정 요청 0건
   → 하나라도 어기면 BusinessError (아무것도 저장하지 않음)
4. db.transaction:
   from = 현재 상태
   NOT_STARTED이면 이력 APP_DRAFTED (NOT_STARTED → DRAFT)
   업무실적·계획 저장, status = SUBMITTED, submitted_at = 지금, return_reason 비움
   이력 APP_SUBMITTED (DRAFT 또는 RETURNED → SUBMITTED)
   알림 APPLICATION_SUBMITTED
```

### C-4. 정정 요청 처리

```
요청 (직원)
  본인·편집 가능 확인 → 항목이 correctable인지 → 같은 항목 PENDING 없는지 → 사유 있는지
  db.transaction: correction_request 추가 (PENDING), 이력 CORRECTION_REQUESTED, 알림

승인 (인사팀)
  요청이 PENDING인지, 회차가 APPLYING·REVIEWING인지
  db.transaction:
    이전 값 = application_item.current_value
    application_item.current_value = appliedValue
    요청: status APPROVED, applied_value, handled_by, handled_at
    이력 CORRECTION_APPROVED (상세: { itemKey, before: 이전 값, after: appliedValue })
    접근기록 UPDATE (정보주체 = 신청자)

반려 (인사팀)
  피드백 필수 → 요청: status REJECTED, feedback … → 이력 CORRECTION_REJECTED (사유 = 피드백)
```

### C-5. 재계산과 변경 감지

```
1. 권한 확인 (HR), rules = loadRules()
2. Mock ERP의 모든 직원, 발령 이력, 수기 대장을 읽는다
3. db.transaction: 직원마다
     calc = calcNextStepDate(입력, rules)
     manual = 수기 대장 값 (없으면 null)
     cmp = compareStatus(calc, manual)
     prev = step_schedule 기존 행 (없으면 null)
     changed = (prev?.autoNextDate ?? null) !== calc.autoNextDate
     행 저장: 직급·호봉·승급일·calc·manual·cmp, calculated_at = 지금 (확정 관련 컬럼은 건드리지 않음)
     changed이고 calc.autoNextDate가 있으면 이력 STEP_CALCULATED (상세: { before, after })
     changed이고 prev.confirmedDate가 있으면
        review_needed = 'Y', 이력 STEP_REVIEW_NEEDED, 알림 STEP_CHANGED
```

> `changed`일 때만 이력을 남기므로, ERP가 그대로면 다시 실행해도 이력이 늘지 않습니다 (멱등성).

### C-6. 승급 안내 발송

```
1. 권한 확인 (HR 또는 SYSTEM), rules = loadRules()
2. db.transaction:
   step_schedule에서 calc_status = 'OK' 또는 확정값이 있는 재직자 중
     isStepNoticeTarget(confirmedDate, today, rules.stepNoticeDays)이면
       queueMail(STEP_NOTICE, dedupKey = `STEP_NOTICE|${사번}|${confirmedDate}`)
   Mock ERP 발령 중 STEP_UP이고 재직자이며
     isStepResultTarget(startDate, today, rules.stepResultDays)이면
       queueMail(STEP_RESULT, dedupKey = `STEP_RESULT|${발령ID}`)
3. 새로 쌓인 메일 목록을 돌려준다
```

### D-1. 원칙

- **명세가 기준입니다.** AI에게 일을 맡길 때는 Step 번호와 요구사항 절을 함께 줍니다.

## E. Git 사용 방법

Git은 **내 컴퓨터에서 버전 관리용으로만** 씁니다. 브랜치나 PR은 쓰지 않아도 됩니다. GitHub에는 마지막 Step 16에서 한 번 올립니다.

### E-1. 언제 커밋하나

- **Step 하나가 끝날 때마다** 커밋합니다 (완료 확인을 모두 통과한 뒤).
- Step이 길면 중간에도 자주 커밋합니다. 함수 하나, 화면 하나처럼 의미 있는 단위가 동작할 때마다 커밋하면 망가졌을 때 되돌리기 쉽습니다.

```bash
# 프로젝트 폴더(promotion-mentoring/)에서
git status                     # 무엇이 바뀌었는지 확인 (.env, .db 가 없어야 함)
git add .
git commit -m "feat(step-05): 승진 대상자 판정 judgeCandidate 구현"
```

### E-2. 커밋 메시지

`종류(step-번호): 설명` 형식으로 씁니다.

| 종류    | 언제               | 예                                                       |
| ------- | ------------------ | -------------------------------------------------------- |
| `feat`  | 기능 추가          | `feat(step-07): 정정 요청 승인·반려 구현`                |
| `fix`   | 버그 수정          | `fix(step-05): 휴직 겹침 일수가 하루 모자라는 문제 수정` |
| `test`  | 테스트만 추가·수정 | `test(step-05): 차기승급일 반복 계산 케이스 추가`        |
| `chore` | 설정, 패키지       | `chore: vitest 설정 수정`                                |
| `docs`  | 문서               | `docs: 회고 작성`                                        |

### E-3. 자주 쓰는 명령

| 하고 싶은 일                                          | 명령                                                                                       |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 커밋 기록 보기                                        | `git log --oneline`                                                                        |
| 커밋 전 변경 내용 보기                                | `git diff`                                                                                 |
| 커밋하지 않은 파일 하나를 마지막 커밋 상태로 되돌리기 | `git restore <파일>`                                                                       |

### E-4. 하지 말 것

- `.env`, `*.db` 파일을 커밋하지 않습니다. 커밋 전에 `git status`로 확인합니다.
- AI 도구가 만든 변경을 확인하지 않고 커밋하지 않습니다. `git diff`로 먼저 봅니다.

| 빌드                    | 배포용으로 코드를 변환·검사하는 과정 (`npm run build`)                                                                              |
| `curl`                  | 터미널에서 주소를 호출하는 명령. 화면 없이 API를 시험할 때 쓴다                                                                     |

**DB**

| 용어                  | 뜻                                                                                       |
| --------------------- | ---------------------------------------------------------------------------------------- |
| DB, 테이블, 행, 컬럼  | 데이터 저장소 / 표 하나 / 표의 한 줄 / 표의 한 칸(항목)                                  |
| PK (기본 키)          | 행을 하나로 구분하는 컬럼. 예: `application_item`은 (신청서 ID, 항목 키)                 |
| FK (외래 키)          | 다른 테이블의 행을 가리키는 컬럼. 가리키는 행이 없으면 저장할 수 없다                    |
| 유일 제약 (unique)    | 같은 값이 두 번 들어갈 수 없게 하는 규칙. 예: `mail_outbox.dedup_key`                    |
| SQL                   | DB에 데이터를 조회·저장하라고 명령하는 언어                                              |
| SQLite                | DB 서버 없이 **파일 하나**(`local.db`)에 저장하는 DB                                     |
| ORM, Drizzle ORM      | DB 테이블을 프로그래밍 언어의 객체처럼 다루게 해 주는 도구 / 이 프로젝트에서 쓰는 ORM    |
| 스키마                | 테이블과 컬럼 구조의 정의 (`src/db/schema.ts`)                                           |
| `drizzle-kit push`    | 스키마 파일의 내용을 실제 DB에 반영하는 명령                                             |
| Drizzle Studio        | 브라우저에서 DB 테이블을 보고 편집하는 도구 (`npm run db:studio`)                        |
| 트랜잭션, 롤백        | 여러 DB 작업을 하나로 묶은 것. 중간에 하나라도 실패하면 전부 취소(롤백)된다              |
| `onConflictDoNothing` | 유일 제약에 걸리면 오류 대신 아무것도 하지 않게 하는 Drizzle 기능. 메일 중복 방지에 쓴다 |
| SQL 뷰 (VIEW)         | 자주 쓰는 조회 결과에 이름을 붙여 테이블처럼 쓸 수 있게 한 것 (P3)                       |
| SQL 인젝션            | 사용자 입력이 SQL 명령의 일부로 실행되는 보안 문제. 값을 파라미터로 넘기면 막을 수 있다  |

**테스트·환경·보안**

| 용어             | 뜻                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------- |
| 단위 테스트      | 함수 하나를 DB 없이 입력·출력만으로 검사하는 테스트 (`*.test.ts`)                                    |
| 통합 테스트      | DB까지 포함해 여러 부분이 함께 동작하는지 검사하는 테스트 (`*.int.test.ts`). `test.db`를 쓴다        |
| Vitest           | 이 프로젝트에서 쓰는 테스트 도구 (`npm test`)                                                        |
| 경계값           | 조건이 바뀌는 바로 그 값. 예: 충족일이 기준일과 같은 E07. 버그가 가장 많이 숨는 곳이라 꼭 테스트한다 |
| 환경변수, `.env` | 프로그램 밖에서 넣어 주는 설정값과 그것을 적어 둔 파일. 비밀정보가 있을 수 있어 Git에 올리지 않는다  |
| 해시 (bcrypt)    | 원래 값을 알아낼 수 없게 변환한 값. 비밀번호는 해시로 저장한다 (Step 13)                             |
| HMAC 서명        | 비밀 키로 만든 값을 붙여, 내용이 위조되지 않았는지 확인하는 방법 (Step 13)                           |
| IP 주소          | 네트워크에서 컴퓨터를 구분하는 주소. 접근기록의 "접속지 정보"                                        |

**Git·호스팅**

| 용어           | 뜻                                                                                                                      |
| -------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Git            | 파일의 변경 이력을 기록하는 버전 관리 도구                                                                              |

| push           | 내 컴퓨터의 커밋을 GitHub에 올리는 것                                                                                   |
| 호스팅, 배포   | 만든 웹 서비스를 인터넷에서 접속할 수 있게 서버에 올리는 것                                                             |
| Vercel         | Next.js를 만든 회사의 호스팅 서비스. GitHub 저장소를 연결하면 자동으로 빌드·배포한다                                    |

| 스케줄러, Cron | 정해진 시각마다 작업을 자동 실행하는 기능 / 그 시각을 적는 형식                                                         |
| Turso          | SQLite와 호환되는 클라우드 DB 서비스 (Step 16에서 해결 방법으로 언급)                                                   |
